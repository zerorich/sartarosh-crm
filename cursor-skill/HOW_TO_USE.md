# Cursor rules: hackathon backend — как пользоваться

Набор правил для Cursor, который при получении текста задачи хакатона сам собирает backend: Node.js + Express + PostgreSQL + Prisma + JWT + Docker Compose, в папке `/server`. Заточен под то, чтобы репозиторий было легко и быстро оценить — читай: если проверяет ИИ-судья или человек за 5 минут, у него не должно возникать вопросов "а где это реализовано".

## Что внутри

```
.cursor/rules/hackathon-backend/
├── 00-overview.mdc                     # всегда активно — стек + пайплайн
├── 01-structure-and-conventions.mdc     # структура папок, слои, формат ответов
├── 02-database-prisma.mdc               # конвенции schema.prisma, миграции, seed
├── 03-auth-and-security.mdc             # JWT, bcrypt, helmet/cors/rate-limit
└── 04-docs-and-judge-optimization.mdc   # README, Swagger, health-check, чек-лист
```

`00-overview.mdc` загружается в Cursor всегда (`alwaysApply: true`) и коротко описывает пайплайн + ссылается на остальные 4 файла. Остальные подключаются автоматически, когда Cursor работает с соответствующими файлами (через `globs`), либо когда сам агент решает, что они релевантны (через `description`).

## Куда положить

Скопируй папку `.cursor/` целиком в корень **нового** репозитория для конкретного хакатона (рядом с будущей `/server`, `/client` и т.д.). Один и тот же набор правил переиспользуется на каждом хакатоне — просто копируешь заново в новый пустой репозиторий.

Если удобнее — можно один раз сделать себе шаблонный репозиторий-болванку (`hackathon-template`) с уже вложенной папкой `.cursor/` и на каждом хакатоне клонировать его вместо копирования вручную.

## Как использовать на самом хакатоне

1. Открой новый (пустой) репозиторий в Cursor.
2. Убедись, что `.cursor/rules/hackathon-backend/` на месте (Cursor подхватывает её сама, ничего активировать вручную не нужно).
3. Открой Agent / Composer, вставь текст условия задачи целиком и попроси собрать backend, например:
   > Вот задача хакатона: [текст ТЗ]. Собери backend в /server.
4. Cursor должен: сначала написать `/server/PLAN.md` (разбор задачи на сущности/эндпоинты — стоит быстро проверить его глазами, это самое дешёвое место поймать недопонимание), потом собрать остальное по пайплайну, и в конце — README с таблицей "требование → эндпоинт".
5. Если по какой-то причине правило не подхватилось само (первый пустой запрос иногда не триггерит) — явно упомяни `.cursor/rules/hackathon-backend` в промпте или введи `@00-overview` в чате.

## Кастомизация под конкретный хакатон

- **Другой обязательный стек** (например, требуют Fastify или MongoDB) — это правило рассчитано именно на Express + PostgreSQL + Prisma; для другого стека проще попросить Cursor в моменте, а `00-overview.mdc` сам скажет, что стек конфликтует с условием.
- **Нужна документация на русском** — по умолчанию весь код, комментарии и README генерируются на английском (стандарт индустрии, безопаснее для любого судьи). Если хакатон явно требует русский — одна строка в промпте, например «README и комментарии — на русском», перекроет дефолт.
- **Нужен TypeScript вместо JS** — правила сейчас написаны под обычный ES-модульный JavaScript (меньше риска, что генерация встрянет на тайпчеке в дедлайн). Если хочется TS — можно попросить меня отдельно собрать TS-вариант, либо попросить Cursor конвертировать уже готовый JS-backend.
- **Нет времени на Docker судьями** — `docker compose up --build` поднимает и БД, и сам API одной командой с автоприменением миграций; это оставлено как есть, потому что именно это чаще всего проверяют первым.

## Чек-лист перед сдачей (для тебя, не для Cursor)

- [ ] `docker compose up --build` с нуля (свежий клон) — поднимается без ручных телодвижений
- [ ] `/server/README.md` открыт, таблица "требование → эндпоинт" реально покрывает всё из условия задачи
- [ ] `/api-docs` открывается и соответствует тому, что реализовано
- [ ] `.env` не закоммичен, `.env.example` заполнен
- [ ] `npm test` (или тесты внутри контейнера) зелёные
